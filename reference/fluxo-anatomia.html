A anatomia de um flow

O minimo necessario para transformar um processo empresarial em um contrato executavel e observavel.

O contrato

Parte Papel Pergunta de projeto
id + namespace Identidade estavel do flow. Onde este processo vive e como sera encontrado?
description Intencao operacional. Que resultado o cliente espera deste flow?
inputs Dados que variam por execucao. O que muda sem justificar uma nova versao do flow?
tasks Passos executaveis. Quais efeitos acontecem e em que ordem?
outputs Resultado consumivel por pessoas ou outros flows. Qual evidencia prova que o processo terminou bem?
triggers Eventos que iniciam execucoes. O processo comeca por pessoa, horario ou evento?

Esqueleto seguro para comecar

Comece com identidade, dados de entrada e saida explicita. Integre servicos externos depois que esse contrato estiver claro.

flow.yaml
id: processo_empresarial
namespace: empresa.operacoes
description: Resultado que o cliente compra

inputs:
  - id: referencia
    type: STRING
    defaults: demonstracao

tasks:
  - id: executar_processo
    type: io.kestra.plugin.core.log.Log
    message: "Processando {{ inputs.referencia }}"

outputs:
  - id: status
    type: STRING
    value: "concluido: {{ inputs.referencia }}"

Regras de bolso

Dados variaveis

Devem ser inputs. Nao clone um flow apenas porque mudou o cliente ou o periodo.

Resultado verificavel

Declare outputs que permitam verificar o efeito sem depender de ler uma mensagem solta no log.

Segredos

Nunca use outputs para senhas, tokens ou credenciais; a documentacao alerta que outputs ficam armazenados em texto claro.
