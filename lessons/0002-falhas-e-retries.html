Robustez não é repetir tudo.

Uma API pode falhar por alguns segundos. Um dado inválido pode falhar sempre. O trabalho profissional é distinguir os dois casos e dar a cada um uma resposta explícita.

Vitória: escolher retry ou tratamento de erro Pré-requisito: lição 01

Retries são uma política para falhas transitórias. Handlers de erro são uma política para o que fazer quando a execução termina em falha.

Retry

Tenta a mesma tarefa novamente dentro de limites de tentativas e tempo.

errors

Executa tarefas de tratamento quando algo falha no flow ou em um bloco.

allowFailure

Permite continuar depois de uma falha aceitável, terminando a execução como WARNING.

Um padrão mínimo de confiabilidade

O bloco abaixo combina uma chamada externa com retry exponencial e um handler global. O intervalo cresce entre tentativas, reduzindo a pressão sobre um serviço que está instável.

billing_sync.yaml 
id: billing_sync
namespace: training.kestra
description: Sincroniza dados de cobrança com limite de recuperação

inputs:
  - id: endpoint
    type: STRING
    defaults: https://example.invalid/billing

tasks:
  - id: call_billing_api
    type: io.kestra.plugin.core.http.Request
    uri: "{{ inputs.endpoint }}"
    retry:
      type: exponential
      maxAttempts: 3
      interval: PT5S
      maxInterval: PT1M
      maxDuration: PT3M

errors:
  - id: alert_failure
    type: io.kestra.plugin.core.log.Log
    level: ERROR
    message: "Falha em {{ flow.namespace }}.{{ flow.id }} / {{ execution.id }}"

O retry não é infinito: maxAttempts conta a tentativa inicial, e maxDuration limita o tempo total. O handler registra o contexto da falha para observação ou alerta.

Decida pelo tipo de falha

Serviço indisponível por instantes

Considere retry exponencial com limites. A falha pode desaparecer sem intervenção humana.

Payload inválido

Retry tende a repetir o mesmo erro. Valide, registre contexto e encaminhe para correção.

Falha não crítica

Use allowFailure somente quando continuar for uma decisão de negócio explícita.

A pergunta que protege o seu serviço

Antes de adicionar um retry, pergunte: repetir a tarefa pode duplicar um efeito? Uma cobrança, envio de e-mail ou criação de registro pode exigir idempotência antes de qualquer política automática.

Traga sua pergunta

Se você não souber se uma falha é transitória, traga o caso concreto. Vamos analisar o efeito, o limite de tentativas e o risco de duplicidade antes de escolher a configuração.

Regra curta

Retry trata instabilidade. Handler trata comunicação e recuperação.

Limites importam

Uma política sem limite pode transformar uma indisponibilidade em tempestade de requisições.
