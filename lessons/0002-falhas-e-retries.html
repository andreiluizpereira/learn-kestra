Robustez nao e repetir tudo.

Uma API pode falhar por alguns segundos. Um dado invalido pode falhar sempre. O trabalho profissional e distinguir os dois casos e dar a cada um uma resposta explicita.

Vitoria: escolher retry ou tratamento de erro Pre-requisito: licao 01

Retries sao uma politica para falhas transitorias. Handlers de erro sao uma politica para o que fazer quando a execucao termina em falha.

Retry

Tenta a mesma tarefa novamente dentro de limites de tentativas e tempo.

errors

Executa tarefas de tratamento quando algo falha no flow ou em um bloco.

allowFailure

Permite continuar depois de uma falha aceitavel, terminando a execucao como WARNING.

Um padrao minimo de confiabilidade

O bloco abaixo combina uma chamada externa com retry exponencial e um handler global. O intervalo cresce entre tentativas, reduzindo a pressao sobre um servico que esta instavel.

billing_sync.yaml 
id: billing_sync
namespace: training.kestra
description: Sincroniza dados de cobranca com limite de recuperacao

inputs:
  - id: endpoint
    type: STRING
    defaults: https://example.invalid/billing

tasks:
  - id: call_billing_api
    type: io.kestra.plugin.core.http.Request
    uri: "{{ inputs.endpoint }}"
    retry:
      type: exponential
      maxAttempts: 3
      interval: PT5S
      maxInterval: PT1M
      maxDuration: PT3M

errors:
  - id: alert_failure
    type: io.kestra.plugin.core.log.Log
    level: ERROR
    message: "Falha em {{ flow.namespace }}.{{ flow.id }} / {{ execution.id }}"

O retry nao e infinito: maxAttempts conta a tentativa inicial, e maxDuration limita o tempo total. O handler registra o contexto da falha para observacao ou alerta.

Decida pelo tipo de falha

Servico indisponivel por instantes

Considere retry exponencial com limites. A falha pode desaparecer sem intervencao humana.

Payload invalido

Retry tende a repetir o mesmo erro. Valide, registre contexto e encaminhe para correcao.

Falha nao critica

Use allowFailure somente quando continuar for uma decisao de negocio explicita.

A pergunta que protege o seu servico

Antes de adicionar um retry, pergunte: repetir a tarefa pode duplicar um efeito? Uma cobranca, envio de e-mail ou criacao de registro pode exigir idempotencia antes de qualquer politica automatica.

Regra curta

Retry trata instabilidade. Handler trata comunicacao e recuperacao.

Limites importam

Uma politica sem limite pode transformar uma indisponibilidade em tempestade de requisicoes.
