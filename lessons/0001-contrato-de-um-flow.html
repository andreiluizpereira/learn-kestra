Um flow profissional começa por um contrato.

Antes de conectar API, banco ou planilha, defina o que entra, o que acontece e qual evidência sai. Esse pequeno hábito evita automações difíceis de reutilizar e vender.

Vitória: criar e executar um flow parametrizado Nível: primeiro contato

Em Kestra, um flow é uma declaração versionável de um processo. A primeira versão não precisa ser grande; ela precisa tornar o contrato visível.

Entrada

O dado que muda entre execuções, como cliente, período ou referência.

Tarefa

Um passo executável que registra, consulta, transforma ou envia algo.

Saída

O resultado que outra tarefa, outro flow ou uma pessoa consegue verificar.

Se um cliente pedir a mesma automação para outra empresa, o que deve mudar: o flow ou os inputs?

O flow da nossa primeira entrega

Este exemplo confirma uma solicitação de onboarding. Ele é deliberadamente pequeno: dois inputs, duas tarefas e uma saída declarada.

onboarding_confirmation.yaml 
id: onboarding_confirmation
namespace: training.kestra
description: Confirma uma solicitação de onboarding

inputs:
  - id: customer
    type: STRING
    defaults: Acme
  - id: request_id
    type: STRING
    defaults: demo-001

tasks:
  - id: announce
    type: io.kestra.plugin.core.log.Log
    message: "Iniciando {{ inputs.customer }} / {{ inputs.request_id }}"

  - id: result
    type: io.kestra.plugin.core.debug.Return
    format: "ready: {{ inputs.customer }} / {{ inputs.request_id }}"

outputs:
  - id: status
    type: STRING
    value: "{{ outputs.result.value }}"

Repare na separação: customer e request_id são dados da execução; announce deixa um rastro no log; status é um resultado que pode ser consumido depois.

Execute e observe

Se você tiver Kestra Cloud ou uma instância local, cole o YAML no editor de flows. Se ainda não tiver ambiente, leia o fluxo como um contrato e use o quiz abaixo; a instalação entra depois, quando a forma do processo estiver clara.

Crie o flow

Use o YAML acima e mantenha o namespace de treinamento por enquanto.

Execute com dados diferentes

Troque customer e request_id para simular dois clientes sem editar a definição.

Confira as duas evidencias

No log, procure a mensagem de announce; na aba de input/output, confira status.

Uma decisão de produto

Quando você vender uma automação, o cliente não compra YAML. Ele compra um resultado repetível. Para cada flow, escreva uma frase de saída que possa ser verificada por alguém que não participou da implementação.

O que guardar

  • Inputs variam por execução.
  • Tasks produzem efeitos.
  • Outputs tornam o resultado verificável.

Alerta profissional

Outputs ficam armazenados no backend. Nunca use outputs para transportar senhas, tokens ou outras informações sensíveis.
